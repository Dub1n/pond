# Relationship schema ergonomics & simplification

## Questions in scope

- What flush bundles are doing and whether we can avoid verbose face/bundle wiring.
- Whether dimension prefixes (`dimensions.structure.*`) can be dropped in favour of semantic names (`cantilever`) and other aliasing.
- How to express multiple relate clauses (align/contact/flush) per component without repetition, including multi-axis intent in a single statement.
- Datums/bundles purpose and whether we can relate directly to faces/edges without defining them separately.
- How grouping/operations work today and what a clearer, composable approach could look like.

## Current behaviour (prep schema + implementation reality)

- Flush bundles: helper that aligns one or more component faces to a datum bundle’s faces with optional per-face insets. It expands to multiple `align` constraints; frame is parsed but currently dropped in the solver (implementation gap).
- Datums/bundles: named reference geometry. Points/planes establish anchors; face bundles define rectangular extents (origin + span) that components snap to. They do not export; they only drive solving/IFC placement.
- Axis tokens: `pos` accepts 1/2/3 signed axes (`+x`, `+x+y`, `+x+y+z`). A single `align`/`contact` clause can therefore solve multiple axes at once against one target. Unspecified axes stay free unless other clauses constrain them.
- Relationship reuse/instancing: `flush_bundle`, `align/contact`, `run_between`, `repeat`, and `assembly.rotate_quadrants` expand clones; `relate_from` exists in the schema but is still unsupported in the solver. `run_between` currently handles arrays along one span with optional rotation (`orient: along_run` limited to XY today).
- Dimension names: the dimension resolver already registers unique leaf-name aliases (`cantilever`, `joist_width`) so prefixes are optional when the leaf is unique; dotted paths still work when disambiguation is needed.
- Operations/grouping: legacy options support end-of-spec `operations` (rotate/mirror) over component lists. Relationship mode relies on assemblies (`rotate_quadrants`), `repeat`, and `run_between`; there is no generic group/operation block yet.

## Ideal longer-term shape

- Reference components replace bundles: geometry-less, non-exporting boxes with `size` + `relate`, single instance, cycle-checked. Components always expose their faces as targets (`ref: component_id`); helpers accept either a component or reference.
- Axis-map `relate` only (no `align`/`contact` keywords): keys are subject axes (multi-axis allowed, canonicalised); values carry the target (`ref` canonical; `component`/`to` aliases), target `pos` (defaults to the key’s axes when omitted), optional `gap`/`offset` (scalar or pos-keyed map, pos keys may be multi-axis), and `mode: plane|edge|point` (default `point`). Centering is explicit via `c*`/`center_*`/`centre_*`/`~*` tokens in keys or target `pos`; nothing auto-centers.
- Checks use the same axis-map shape, so coplanar/colinear assertions use `mode: plane|edge` with explicit center tokens when needed.
- Size inference from relations: axis pairs in `relate` (any combination of + / - / c per axis) can back-fill missing `size` axes; conflicts with explicit `size` are lint errors unless the values match.
- `run_between` accepts component/reference targets, supports center tokens in `start_pos`/`end_pos`, and does not implicitly fill missing axes.
- `flush` stays as sugar over multiple axis-map entries; allow component/reference targets, `faces: all` default, scalar `inset` for symmetric cases, structured per-face inset retained.
- Operations stay typed (`rotate`, `mirror`, `translate`, `boolean`) targeting components/groups post-solve; groups are schema-level lists.
- Reference-only leniency: references may omit `relate`; when axes are omitted on references, they default to 0 (origin) to avoid boilerplate. Components must still name the axes they intend to solve (or use explicit center tokens); missing component axes should lint.
- Placement helper: `place` creates instances with per-placement axis-map blocks; within `place` entries, the axis-map is used directly (no extra `relate` key).
- ID selectors for aggregates: allow `id` (all instances), `id.original` (seeds/place entries), and `id.clones` (generated by rotate/mirror/other ops) anywhere a list of components is accepted (operations, booleans, groups, checks). For templates with `place`, `id` spans all placements and their clones; for a single placement `foo_bar`, `foo_bar.original` is just that seed, `foo_bar.clones` its transformed copies.

## Implementation report (relationship-first surface, March 2024)

### Scope delivered

- Replaced legacy align/contact parsing with the axis-map shape: subject axes → `{ref,pos,gap,offset,mode,frame}`, supporting multi-axis tokens and center tokens (`c*`, `~*`), with `flush` sugar expanding to axis-map entries (`faces: all` default, scalar/per-face inset).
- Added reference components (`kind: reference`) with lenient defaults (missing axes → 0) plus size inference only for regular components; explicit size conflicts lint unless matched.
- Added size inference from relate pairs; components must declare or infer X/Y/Z, references may omit axes.
- `place` uses inline axis-map blocks per placement (no nested relate); `run_between` accepts component/reference targets, center tokens in `start_pos`/`end_pos`, `orient: along_run`.
- Aggregate selectors (`id`, `id.original`, `id.clones`) are accepted across operations/booleans/checks/groups; typed operations implemented (`rotate`, `mirror`, `translate`, `boolean`) with rotation id maps and selector expansion.
- Lint: validates axis coverage (components must constrain all axes), inferred-vs-explicit size conflicts, selector/target existence, frame references; solver-backed lint path via `scripts/lint_specs.py` now runs IFC/unit checks and emits mesh digests.
- Solver: resolves axis-map relations with size inference, run_between arrays, selector-aware operations, deterministic GUIDs, OCC collision detection (severity via `DIAGRAM_RELATIONSHIPS_COLLISIONS`), neutral primitives (box/wedge/sweep) with stored meshes/footprints.
- Planner: relationship planner projects plan/section footprints from solver primitives and emits dimension polylines; renderers unchanged.
- Docs/tests: refreshed `architecture-spec.md`, `AGENTS.md`, `docs/instructions.md`; test suite rewritten around axis-map parsing/solver/planner/validation; Option C spec updated with missing dimensions.

### Known gaps / follow-ups

- Relationship `groups` are not yet separate schema entities; operations run on selectors directly.
- Collision volumes are reported but not filtered by class/material; no auto-resolution.
- IFC export relies on provided `class`/`predefined_type`; missing mappings still lint as errors.

### How Option C changed

- Added missing dimensions (`corner_diagonal_length`, `corner_tie_spacing`) to keep the compact schema valid.
- Simplified corner diagonal relate to avoid four-way axis pairs; remains to be finalized with a single span to stop inference conflicts.
- Build currently succeeds to solver output with collisions downgraded via `DIAGRAM_RELATIONSHIPS_COLLISIONS=warn`

### Usage notes

- Prefer one X and one Y axis pair when you want size inference; extra pairs can conflict with explicit `size`.
- Use center tokens (`cx`, `cy`, `cz`) to avoid mixed-sign pairs when anchoring symmetric geometry.
- Keep references lean: omit relate entries you don’t need; components must cover all axes or supply explicit sizes.
- Selectors make boolean ops and rotations declarative; ensure `id_map` covers numbered instances when rotation clones are expected.
